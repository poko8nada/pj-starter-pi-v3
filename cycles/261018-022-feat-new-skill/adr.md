# ADR 022

## 01: `brief` の収束点と手順

### Context

- ADR の前段を独立させることになり、owner が起点の側を `brief` と呼ぶ。
- `brief` の担当は 4 つある。情報を調べること、owner の意図を詰めること、選択肢を出して吟味すること、どれにするかを決めることである。
- `brief` が終わった時点で、ADR の `Context` と `Options` と `Research & Trial` が埋まっている状態を目指す。
- 調べる範囲は 3 つの型に固定する。公式情報、ソースコード、実際に使われている形を書いた記事の 3 つである。
- プロジェクトのソースコードは主な入力ではない。
- `brief` はファイルを作らない。`memo-*` は使ってよいが、残す義務は無い。
- 調べた情報はその時点で必要だったものであり、ADR に持ち込まなくてよい。必要になったら調べ直す方が新しい。
- 収束点は、選択肢が複数あることではない。owner の意図が言葉になり、その意図を満たす選択肢が吟味され、どれにするか決まることである（owner の判断）。
- 収束点は 4 つある。対象が 1 つに決まっていること、`Context` が埋まっていること、`Options` が埋まり採らなかった理由が一言で言えること、決定が乗る事実が `Research & Trial` に書けることである。
- `propose` の収束点も同じ 4 つで、ADR の前段はどちらもここで終わる。
- 手順は一方向ではない。意図を議論し、調べる内容を提案して承認を受け、調べ、選択肢を出して議論し、必要なら追加の調査とトライアルを行い、吟味して決める。行き来してよい。
- 調べるのは意図が固まってからにする。宣言文だけで調べ始めると、対象が見当違いになる（owner の判断）。
- トライアルは実現性の確認に使う。対象は Stack か、その場で簡単にできる確認事項である。選択肢を捨てる材料になる。
- `brief` が決める場合、ADR に残るのは定義の変化、entries の突き合わせ、記録になる。この扱いは 03 で決める。
- 残す価値があるのは採らなかった案と一行の理由であり、それは ADR の `Options` に既にある。
- 共通部分は抜き出さない。`brief` を先に完成させ、同じ部分を `propose` に転記する。内容が同じでも独立した 2 ファイルにする（owner の判断）。
- `brief` はハーネスの一部で、クローンした先のプロダクトでも同じように動く。書くときに使う名前は、ハーネスが配る物に限る。`DEFINITION.md`、`cycles/`、`close.md` の `Triage`、`Unit`、`Stack`、`Who` である。
- この repo の中身（スキル、拡張、検査の道具）は名前を出さない。プロダクトの中身はクローン先で決まる。
- 022 自身はこのスキルが無い状態で始まるので、前段を会話で手で回した。その整理がこの ADR の Context である。
- description の文言は 03 で決める。

### Decision

- Status: **accepted**
- Adopted:
  - 意図は、エージェントが「こう理解した」と先に書いて owner に直してもらう形で詰める。争点が消えるまで重ねる。
  - 調べる内容は 3 つの型から選ぶ。公式情報、ソースコード、実際に使われている形のどれを何に当てるかだけを提案し、owner が承認してから調べる。
  - 承認された範囲だけを調べ、結果は分かったことと分からなかったことに分けて出す。
  - 選択肢を 2〜4 個出す。各案に、得る物と失う物と実現性の引っかかりを添える。
  - 選択肢を議論して 1 つに絞る。実現性に不安があれば、その案だけトライアルを行う。
  - owner が「これで行く」と言った時点で終わる。
- Options:
  - 意図の確認と調査内容の承認を 1 往復にまとめる（owner が上の形を選んだ。理解の確認と計画の承認は別に置く）。
  - 調査内容を出さずに調べ始める（見当違いの調査がそのまま費用になる）。

### Research & Trial

- 未実施。

### Definition Change

- `Unit.brief-skill`(added): エージェントが、サイクルの要件を調べ、詰めて、ADR に渡せる

## 02: `propose` の手順

### Context

- サイクルを始めるのは基本 owner だが、エージェントからも議題を提案させたい。
- 提案は 3 つの問いを 1 回で行う（owner の判断）。積み残しが無いか、Unit として何が新しくあるべきか、現行の Unit に不要なものや統合できるものは無いかである。
- 手順は、まずコードベースを探索することから始める。リサーチはその探索と並行して走らせる。
- 重さでは分けない。毎回 3 つとも回すかどうかは、スキルを実行するかどうかで決まる。
- 積み残しは `close.md` の `Triage` の `proposed` と、`archive` の ADR の `rejected` から出す。
- 新しい Unit は `DEFINITION.md` の全行と `Who` の `Needs` から出す。
- 棚卸しは `DEFINITION.md` の全行を `definition/rules.md` の規則に照らして行う。
- `close` の triage には `proposed` という行き先がある。次のサイクルが引き取る約束だが、`cycles/` には 1 件も無い。引き取る側がいないまま運用されている。
- 収束点は `brief` と同じ 4 つである。対象が 1 つに決まり、`Context` と `Options` と `Research & Trial` に書く材料が揃っている（owner の判断）。
- 候補には、どの Unit が動くかを添える。ここが `brief` と違う。絵のどこが変わるかを言えないと、owner が大きさを測れない（owner の判断）。
- 共通部分は `brief` から転記する。内容が同じでも独立した 2 ファイルにする。
- `propose` もハーネスの一部である。使う名前はハーネスが配る物に限り、この repo の中身は名前を出さない。
- description の文言は 03 で決める。

### Decision

- Status: **accepted**
- Adopted:
  - 3 つの問いを 1 回で回す。積み残し、新しい Unit、棚卸しの順である。
  - まずコードベースを探索する。リサーチはその探索と並行して走らせる。
  - リサーチは `brief` と違って承認を取らない。探索で範囲が決まるので、先に見当を外すことが少ない。
  - リサーチの型は `brief` と同じ 3 つ（公式情報、ソースコード、実際に使われている形）である。
  - 積み残しは `close.md` の `Triage` の `proposed` と、`archive` の ADR の `rejected` から出す。
  - 新しい Unit は `DEFINITION.md` の全行と `Who` の `Needs` から出す。
  - 棚卸しは `DEFINITION.md` の全行を `definition/rules.md` の規則に照らして行う。
  - 各候補に、なぜ今か、どの Unit が動くか、根拠を添える。
  - 推奨を 1 つ添える。owner は選ぶか、その回は見送る。
- Options:
  - 記録と定義だけで回し、実物を読まない（棚卸しと新しい Unit の判断が浅くなる）。
  - 実物まで読む回と読まない回を分ける（毎回の形が変わり、出す内容が揃わない）。
  - 棚卸しを owner が求めた時だけにする（不要な Unit が残り続ける）。

### Research & Trial

- 未実施。

### Definition Change

- `Unit.propose-skill`(added): エージェントが、プロジェクトの状態から次の議題を提案できる

## 03: ADR 側の調整

### Context

- 前段が `Context` と `Options` と `Research & Trial` を埋めて ADR に渡すなら、entry 2 の talk と重なる。owner が同じことを 2 回聞かれる。
- `Research & Trial` の役割は狭くなる。調べたことの置き場ではなく、決定がその事実に乗っている場合だけ書く場所になる。
- `brief` か `propose` が決めるなら、ADR の `Decision` は owner の答えを写す場所になる。写すだけなら、ADR に残る仕事は定義の変化と entries の突き合わせになる。
- いま `adr` の description は「owner がサイクル開始を宣言したら」で発火する。`brief` に宣言を移すなら、こちらを狭める必要がある。
- 決めることは 4 つある。entry 2 を書き換えるか消すか、entry 4 をどう狭めるか、description を狭めるか、`references/format.md` を変えるかである。

### Decision

- Status: **accepted**
- Adopted:
  - entry 2 は「前段の記録を `Context` に落とす」に書き換える。talk は `brief` 側にあるので、ここでは繰り返さない。
  - `Research & Trial` は「決定の根拠だけを書く」に狭める。前段で調べたことは書かない。
  - `adr` の description を狭める。`brief` か `propose` を経た問いだけを受ける。サイクル開始の宣言は `brief` が受け、次に何をするかの問いは `propose` が受ける。
  - `references/format.md` は変えない。節の名前はそのままにする。
- Options:
  - entry 2 を消し、`Context` は前段から来ると SKILL.md の頭に書く（短いが、番号が飛ぶ）。
  - `Research & Trial` をそのまま残す（前段の調査も書けるが、置き場が二重になる）。
  - `adr` の description を広いまま残す（サイクル開始の宣言でも ADR に入る）。
  - `format.md` の節の名前を変える（前段から来た内容に合わなくなる）。

### Research & Trial

- 未実施。

### Definition Change

- `Unit.adr-skill`(updated): エージェントまたは owner が、決めるべきことを決めて記録できる
